# Protocol — git-resolve-conflicts

Full step detail for this skill. `SKILL.md` is the entrypoint and holds the constraints; this file holds the per-conflict analysis and the continue loop.

## Step 1 — Identify the Operation

A rebase or cherry-pick replays many commits, so it can stop repeatedly; a merge stops at most once. Determine which you are in before touching anything:

```bash
git status
ls .git/rebase-merge .git/rebase-apply .git/MERGE_HEAD .git/CHERRY_PICK_HEAD 2>/dev/null
```

| State | Continue command |
| --- | --- |
| `.git/rebase-merge` or `.git/rebase-apply` | `git rebase --continue` |
| `.git/MERGE_HEAD` | `git merge --continue` |
| `.git/CHERRY_PICK_HEAD` | `git cherry-pick --continue` |

If none of these exist there is no operation in progress — say so and stop rather than starting one.

During a rebase, `git status` also reports progress ("interactive rebase in progress; onto abc1234, last command done, 3 remaining"). Track that count: it is how you know the loop is advancing.

Note the current commit's subject before resolving. You need it for both the no-progress check and the final summary.

## Step 2 — Analyze Each Conflict

Find the conflicted files:

```bash
git status --porcelain
git diff --name-only --diff-filter=U
```

Look for "both modified", "both added", "added by us/them", "deleted by us/them". A delete/modify conflict has no markers in the file — it is resolved by choosing `git add <path>` (keep) or reporting it (the delete side needs a `git rm`, which this skill does not run; stop and ask).

For each conflicted file:

1. **Read the whole file**, not just the hunk. A resolution that is locally plausible and globally wrong is the main failure mode here.
2. **Work out what each side intended.** In a rebase the labels are inverted from what people expect: `HEAD`/`ours` is the upstream commit you are replaying *onto*, and `>>>>>>>` /`theirs` is *your* commit being replayed. In a merge it is the other way round. Read the branch names in the markers rather than assuming.
3. **Classify the conflict:**
   - Additive — both sides added different things. Usually keep both.
   - Modification — both sides changed the same thing. Merge the intents if they compose; escalate if they contradict.
   - Deletion — one side deleted what the other changed. Rarely auto-resolvable; prefer asking.
4. **Check whether it is critical** — API signatures, schema/migrations, lockfiles, generated files, public contracts. Critical conflicts get a stricter bar: if you cannot justify the resolution from the code in front of you, stop.

Lockfiles and other generated artifacts should be regenerated by their tool, not hand-merged. This skill cannot run those tools — stage nothing, and tell the user which command to run.

## Step 3 — Resolve and Stage

Edit with `Edit`/`MultiEdit` so that all markers are gone, syntax is valid, and the file's existing style holds. Then:

```bash
git add <path>
git diff --check
git diff --name-only --diff-filter=U
```

The last command must print nothing before you continue. Do not continue an operation with unmerged paths still present.

## Step 4 — Continue the Operation

Run the command from Step 1 with a non-interactive editor, or it will hang waiting on a commit message:

```bash
GIT_EDITOR=true git rebase --continue
```

Read the result rather than assuming success:

- **Finished** ("Successfully rebased and updated", or a clean `git status`) — stop and write the summary.
- **New conflicts** — return to Step 2 for the next commit.
- **"No changes -- did you forget to use 'git add'?"** — either you missed staging a file (fix and retry once), or your resolution made the commit empty because upstream already contains it. An empty commit is resolved with `--skip`, which drops a commit. Do not run it. Stop and ask.
- **Any other error** — stop and report it verbatim. Do not improvise a recovery.

## Step 5 — Loop Control

Loop back to Step 2 for each new set of conflicts. Stop immediately when:

- The operation completes.
- A conflict is genuinely ambiguous, critical-and-unjustifiable, or a delete/modify.
- Git asks for `--skip` or reports an error you did not anticipate.
- **No progress:** the same commit stops with the same conflicting paths twice in a row. That means your resolution is not sticking. Report the commit, the paths, both attempts, and your best theory — do not try a third time.
- The remaining-commit count has not decreased across two continues.
- You have replayed more than 20 commits. Report where you are and confirm before continuing; a rebase that long usually wants a different strategy.

The user asked for the loop so they do not have to run `--continue` by hand. They did not ask you to force the operation through — an early, well-explained stop is a success, a fabricated merge is not.

## Step 6 — Summary

Report, in this order:

1. Operation type and its final state (completed, or stopped at commit X of Y).
2. Per commit, per file: what conflicted and how you resolved it.
3. Every place you chose one side over the other, with the reason.
4. Anything you are uncertain about, called out plainly so the user knows where to look.
5. If stopped early: the exact blocking condition and the command the user should run.

Do not claim the tree is good without evidence. You have not run the tests — say so, and suggest the user do it before pushing.
